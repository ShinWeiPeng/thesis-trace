### Fee-aware sizing implementation detail (accepted ALG-0012 / ADR-0009 conformance)

Portfolio snapshot persistence extends the existing PortfolioStorePort with append/get operations taking only actor identity and PortfolioRecommendationSnapshot. The existing PostgreSQL Portfolio adapter owns three new append-only forced-RLS relational tables: a flattened snapshot header (cash, version, cost inputs, target metadata, sizing and policy results), ordered complete holding rows, and keyed exposure rows. SQLAlchemy mappings are adapter-private construction-local schema objects, not new domain/global runtime state. Historical reads reconstruct only frozen rows, never join mutable current holdings, official metadata or costs. The parent remains responsible for admission/publication source fencing and invokes this participant only inside the approved atomic operation; append alone is not a Recommendation publication or trade. `portfolio.policy.select_dca_multiplier` receives an explicit analytical `buy_price` and Portfolio-owned `CostProfileSnapshot` in addition to the existing official-price/classification inputs. Candidate notional is base times multiplier, fee is the maximum of minimum fee and proportional buy fee; acquired quantity uses buy price while acquired market value uses official close. Cash decreases by notional plus fee; post-trade NAV includes the resulting mark-to-market difference. Missing/invalid Cost Profile fails closed. This is a pure Portfolio calculation and does not publish or trade.

### Publication policy implementation detail (accepted ALG-0032)

It does not perform database publication, source reads or challenge consumption. ## Candidate / Flow cost review

| Dimension | A: isolated AI + atomic owner transactions | B: request-thread AI | D: isolated AI + durable Workflow subscriber |
| --- | --- | --- | --- |
| Functional admission | preserves worker isolation, owner authority and immediate decision/task consistency | fails REQ-011 / DEC-080 | viable with durable publication/subscriber/reconciliation, but eventual task consistency |
| Path | admit tx → queue → provider → critic → publish+task tx; preview → confirm+decision+task tx | admit → provider/critic while request remains active → commit | A's analysis then extra durable event → claim → Workflow tx |

| Evolution | additional source touches Research + parent mapping; new model touches adapter/schema tests | provider latency change directly affects API | additional independently durable subscribers have better isolation |
| Tradeoff | more transaction participants/lock contention and shared AI-worker contention | less queue plumbing but unsafe isolation | looser coupling, more operational state and delayed task outcome |

An actual Wave 7 build does not yet exist, so numeric observation, prediction error and measured headroom are **not available**, not zero. Model assurance: **estimated** for logical cost only. ## Accepted execution and reliability contract

Queue persistence detail: RecommendationJob additionally carries scalar actor/Thesis/cycle identity so composition can create an Owner-scoped binding after a worker claim; no role is inferred from a provider. Immutable admissions use separate normalized headers, ordered bindings/sources and pinned version pairs, not a mutable input JSON aggregate. Request receipts bind actor/key/digest. A Recommendation-owned capacity row counts all nonterminal jobs without exposing other owners' requests to an API session. A fixed-search-path SECURITY DEFINER trigger updates only that counter under a row lock; API/worker roles have no direct counter-table privileges. This is an implementation of the accepted global 1000 cap, not a capacity/performance claim or new cross-owner query API. Queue claim/lease metadata is readable globally only by the existing database AI-worker role through a named RLS policy; API reads remain exact-Owner scoped and do not receive job UPDATE privileges. Worker source/result operations still use explicit Owner context and parent-owned revalidation. Stable stream serialization uses the durable processing lease plus a partial unique index on Owner/Thesis/cycle; each claim reclaims expired work with a fresh token and rejects attempts beyond three. No source locks remain held during provider calls.

Reuse existing `api_process` and `ai_worker_process` on `linux_server_functional`; no new OS process, core affinity, priority, RTOS, real-time workload, cache/SIMD/PGO or platform variant. Add a typed `recommendation-analysis-v1` channel. Numeric values here are explicitly accepted safety/operational limits, not measured capacity claims:

- Admission cap: 1000 nonterminal recommendation jobs, checked atomically; reject overloaded admission without a partial request. This does not prove the VM can sustain combined anomaly+recommendation backlog; shared-resource acceptance is still required.
- Claim one job at a time, order by available time then stable job ID; serialize by Owner/Thesis cycle. Pin build, input, policy/model/prompt/schema, idempotency and correlation/causation metadata. Different subjects are eligible independently; no same-stream reentry.
- Lease 300 seconds, matching the existing architecture channel budget; database UTC clock is authority. Renew/fence between provider and critic, and before commit; reject any completion with an expired/stolen token. Never hold a DB transaction during network I/O.
- Each provider and critic call has a **total** 30-second deadline and a response-body cap, not merely a per-socket-read timeout. Three maximum attempts; retry only transient transport failures at 1 and 4 minutes after attempts one/two. Third failure is dead-letter. Schema/citation/critic failures are terminal safe failures, not provider failover triggers. A crash reclaim uses a new attempt and the same immutable inputs; no partially mixed outputs.
- Worker iteration offers one expiry reconciliation item, one anomaly attempt and one Recommendation attempt in that order, then repeats; use existing two-second idle wait only when no work was done. Work in one class must not be skipped because another class had work. This is bounded cooperative service, not a real-time or fairness-latency guarantee.
- Expiry persistence is restart-safe and idempotent. Dead-letter/failure status is exposed in the Owner company view; the general operational alert delivery pipeline remains a separately required follow-on gate, not claimed implemented here.
- Input bounds: at most 32 sources with at most 2048 characters of excerpt each and 256 KiB total encoded provider input; at most 32 candidate claims of 2048 characters each, with an independent 64 KiB encoded response cap for provider and critic. Oversize rejects; never silently truncate a decision-critical claim. Pinned references are retained even when an analysis cannot be admitted under these limits.

The accepted financial policies are reused after fixing discovered implementation drift. This new job type does not silently accept or rewrite the generic proposed ALG-0022 or change anomaly retries.

## UI and recovery contract

Admission transaction detail: RecommendationAdmissionCommand is a parent-owned immutable scalar intent containing authenticated Owner/account version, expected Thesis/valuation/Portfolio versions, explicit benchmark source/reason and idempotency key. RecommendationTransactionPort.admit returns only the input ID. The concrete coordinator revalidates Access, asks Recommendation's own store for the actor/key/command-digest receipt under the same transaction lock, and returns an exact existing admission before resolving any new source/Clock values. New admission then acquires Thesis, sorted Evidence and Owner Portfolio fences, maps current owner queries through L0, and stores the immutable input, audit and one job together. New IDs come from a composition/adapter-local ID factory, never a browser record ID. The canonical intent digest excludes newly generated IDs and admission time. Identical concurrent retries share the original job even if current data changed after it was admitted; changed intent on the same key is rejected. No AI I/O occurs in this operation. This is the accepted idempotent admission contract, not a grant to replay an old account after Access revocation.

Runtime grant inventory: extend the existing one-shot migration role's explicit grants for the new Recommendation schema and immutable Portfolio snapshots. API may admit/read requests and append Owner decisions but cannot UPDATE jobs or touch the queue-capacity row. The AI worker may claim/fence jobs, read only required Research/Thesis/Portfolio inputs under Owner RLS, append Recommendation/risk/Workflow outcomes, and execute the narrow Access Owner-lock function; it receives no account UPDATE, cash/holding mutation, Trade INSERT or source-fact mutation grant. Both decision writers receive only column-level UPDATE(version) on immutable Recommendation headers to support their existing row-lock trigger; the unconditional append-only trigger rejects actual UPDATE, including no-op updates.
